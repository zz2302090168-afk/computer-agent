# 装机研究所 · 电脑推荐与智能客服 Agent

中文对话式主机选配项目，使用 TypeScript、Next.js 和 MySQL，面向单商家私有部署。模型负责理解需求、查询候选和选择工具；程序负责商品来源、八类完整性、报价、预算、配色与兼容性审核。

用户可以从自然语言需求开始，完成商品查询、多档推荐、方案选定、局部替换、整单确认与 Word 配置单导出，也可以咨询整机商品和售后问题。预算、用途齐全的配机请求同轮继续推荐；纯咨询、只查替换候选和明确暂不生成保持各自的操作边界。

## 技术与调用链

| 层次 | 技术与职责 |
| --- | --- |
| 页面 | React 19、Next.js 16 App Router、TypeScript、Tailwind CSS |
| 服务端 | Next.js Node.js 运行时、Function Calling 对话循环与业务工具 |
| 数据 | MySQL 8、mysql2 连接池与参数化 SQL、Drizzle 表定义和迁移 |
| 约束搜索 | 八类候选域、价格界剪枝、已知兼容冲突过滤与统一交付审核 |
| 知识 | OpenAI 兼容 Embeddings 接口、余弦相似度、进程内语料向量缓存 |
| 验证 | TypeScript、Oxlint、Node.js 测试与生产构建 |

```text
用户消息 → 页面会话与商品目录 → 本轮动作与结构化需求 → 业务工具
                                                     ↓
                                    候选搜索 / 并行选型 / 局部替换
                                                     ↓
                                 最新目录统一审核 → 版本校验与内存更新
                                                     ↓
                                       NDJSON 进度与最终结果 → 页面
```

工具可见范围、运行时参数、用户授权和交付结果分别校验；流程结束依据结构化动作和工具执行事实，不根据助手回复中的关键词强制生成。页面按钮与聊天工具共用业务服务。

## 页面会话

对话采用一次性页面会话：聊天、需求、方案、选定确认和售后进度只在内存中临时保留。进入商品目录时聊天界面暂时隐藏，正在输出的回复和配置生成继续进行；返回聊天后可查看当前进度或最终答复。刷新任一页面（包括目录页）、关闭页面或开始新会话均结束本次对话，重新打开时清空，不写入数据库或浏览器持久存储。不提供多任务、历史记录、旧方案恢复或撤回。MySQL 继续提供商品目录。

后端排查例外：聊天调用链的消息、目录快照、模型与工具调用、状态和错误可写入服务器 `logs/chat/*.jsonl`，仅供开发排查和测试，不用于恢复会话，不提供前端入口。默认保留最近 100 轮，每轮上限 8 MiB（超限记录截断标记），已知环境密钥和认证字段脱敏；日志不进入 Git。部署需使用可写且持久的服务器目录，临时容器销毁会丢失本地日志。

## 本地运行

需要 Node.js 22.13+ 和 MySQL 8。Windows 首次运行先安装项目使用的 pnpm，并确认命令可用：

```powershell
npm install --global pnpm
pnpm --version
```

若安装成功后当前 PowerShell 仍提示无法识别 `pnpm`，先执行下面一行刷新当前窗口的 PATH；以后新开的终端会直接读取永久 PATH：

```powershell
$env:Path = "$env:APPDATA\npm;$env:Path"
```

克隆仓库后安装锁定依赖，首次运行时复制环境模板；已有 `.env.local` 不要覆盖：

```powershell
git clone https://github.com/zz2302090168-afk/computer-agent.git
cd computer-agent
pnpm install --frozen-lockfile
if (-not (Test-Path .env.local)) { Copy-Item .env.example .env.local }
```

先创建使用 `utf8mb4` 的独立 MySQL 数据库与最小权限账号，再编辑 `.env.local`，至少填写数据库、模型和 Embedding 配置。完成后执行：

```powershell
pnpm db:migrate
pnpm dev
```

访问 [本地页面](http://localhost:3000)。迁移建立 MySQL 表，首次读取相应目录时初始化种子商品；刷新不会读取以前保存的聊天或方案。

**已有版本升级：** `drizzle-mysql/0002_drop_persisted_chat.sql` 会删除旧 `conversations`、`task_history`、`tasks` 表及其中记录。执行迁移前备份需要保留的数据；该迁移不删除商品表，当前应用不提供旧对话恢复。

在同一个 `.env.local` 配置 `MODEL_BASE_URL`、`MODEL_NAME`、`MODEL_API_KEY` 以及 `EMBEDDING_API_KEY`、`EMBEDDING_BASE_URL`、`EMBEDDING_MODEL`，然后重启服务。模型地址使用 HTTPS，基础地址包含 `/v1` 等前缀；服务需支持 Chat Completions、工具调用和 SSE streaming。Embedding 基础地址填写到 `/v1` 等 API 前缀，不包含末尾 `/embeddings`，程序会自动追加；服务需支持 OpenAI 兼容 Embeddings 接口。密钥只保存在服务端，不提交 Git。当前聊天流程需要模型配置，不能将底层规则搜索视为独立的无模型聊天模式。

| 环境变量 | 用途 |
| --- | --- |
| `DATABASE_URL` | MySQL 连接串，格式参见 `.env.example` |
| `MODEL_BASE_URL` | 模型 API 基础地址，不包含末尾 `/chat/completions` |
| `MODEL_NAME`、`MODEL_API_KEY` | 模型名称及认证密钥 |
| `EMBEDDING_BASE_URL` | 向量 API 基础地址，不包含末尾 `/embeddings` |
| `EMBEDDING_MODEL`、`EMBEDDING_API_KEY` | 独立的向量模型名称及认证密钥 |

可发送“8000 元，主要玩游戏，DIY，黑色优先，白色备选”开始试用。实际结果取决于当前目录和审核结果；先选定方案再讨论替换，确认后可导出 Word，刷新会清空这次对话。

## 当前功能

- 本次连续对话临时保留需求和方案，刷新页面开启空白对话。
- 正常推荐在同一预算允许区间内探索低价、均衡、高价方案。服务端先搜索候选，再并发执行模型选型；候选不足时如实展示，不重复凑数。明确最贵、最便宜或预算极端参考使用单套方案。
- 模型流式响应在服务端组装；聊天接口以 NDJSON 推送当前查询、选型、修正与审核进度。共享候选准备完后，低价、均衡、高价方案独立并行，固定三卡原位更新，详细过程默认折叠，不逐条自动滚动。
- 每套方案经过最新目录审核后即可展开只读预览，不必等其他分支。整批最终重审并写入本次对话内存后才允许选择、替换或确认；失败或新一轮生成会移除失效预览，候选不足三套时如实展示实际数量。每个独立方案分支最多提交 3 个不重复候选组合进行修正，目录只读查询不计入修正次数，不能重新启动推荐来重置本轮额度。选型结束或超时后，已有逻辑可能复核尚未提交失败的原始程序候选，仍必须通过审核。
- 配置交付、局部替换和确认均经过统一程序审核。未知规格保留待确认；缺少 BIOS、接口或尺寸资料时，知识检索只能提供证据，不能绕过兼容性审核；不编造规格、FPS、1% low 或性能统计。
- 知识检索使用 Embedding 向量召回，语料向量按服务地址、模型和内容缓存在服务进程内；用于知识问答、选型解释和评估依据，不参与商品选型、报价计算或兼容性审核。当前没有向量数据库或最低相关度阈值，召回分数不等于正确率。
- 售后向量服务失败时，只有明确指定有效故障主题才读取本地同主题资料；空匹配不会扩展到其他主题。排查正文由程序直接呈现本轮实际选中的步骤或澄清知识块，没有适用资料时只提供受控澄清问题，不交付模型自由补写的操作。来源说明、停止条件和结论块不能当作下一步；一次只选一步，等待用户反馈后继续。停止排查、人工请求和恢复反馈按实际状态呈现，不因检索失败自动转人工。

售后资料覆盖通用流程、不通电、无显示、系统启动、蓝屏重启、卡顿冻结、过热噪声、网络、外设与数据 9 个主题，属于未经具体厂家逐项验证的通用指导。当前只能记录人工协助请求，没有实际接通客服、发送通知或创建工单的接口；用户反馈恢复也不代表根因已经确认。

## 方案选择与局部修改

`select_plan` 在本次对话临时记录用户选定的具体方案，选择与最终确认分开；页面按钮与聊天工具共用业务服务。后续解释、评估、替换查询和局部修改可以使用已选定或唯一方案，多套未选定时必须明确对象；刷新后这些状态不再保留。

`find_replacements` 支持单件查询和 `items` 数组指定的多件联动查询，固定未指定的配件，对每个组合整体审核，返回总价、兼容性、拒绝原因、颜色变更预览和分页。它不修改配置；用户允许替换后再调用 `replace_parts` 一次提交整组并重新审核。组合按类别顺序和各类价格展开分页，不代表全局总价排序；一页无可用项不能推断整个目录无解。

替换查询条件和结果随本次对话在内存中保留，供下一轮继续引用。同方案新增联动类别时，原类别省略的过滤条件沿用最近查询；明确取消型号或品牌条件时传空字符串，取消颜色限制时传“不限”。查询记录不改变配置和确认状态。

用户询问某款配件或整套方案的选择原因时，`explain_selection` 只读返回当前商品规格、用途约束、知识库依据和候选排序共用的预算分配权重。回答聚焦为什么适合当前需求，可按八类详细解释，不追溯淘汰其他候选，不修改配置。询问改进或比较时使用只读评估；只有用户明确接受具体建议才执行。多条建议下“这个”等指代不清时先澄清，不自动执行。权重表示业务预算偏好，不是模型内部参数或实测性能。

已有 DIY 方案只换一件或几件时，模型先查询新商品，再调用 `replace_parts`；页面替换入口使用同一业务服务。未指定替换的配件 ID 保持不变，整体重新报价与审核。替换失败时原方案保留，不自动换掉其他配件来凑预算。多套方案指代不清时需先确定哪一套；修改成功后保留被修改的这一套，其他旧候选不继续冒充符合新需求。

例如：

- “均衡方案的显卡换成5070，其他不动”：只替换该套显卡。
- “机箱换白色，其他保持”：只替换机箱，单独记录机箱颜色。

商家整机只接受目录内实际组合，不能当作 DIY 拆换；转为 DIY 需要用户明确同意。

右上角商品目录默认展示组装整机，也可切换 DIY 配件和显示器。整机支持型号、品牌、标注颜色及价格筛选、排序和分页，展开查看八类构成；售价使用整机记录，演示商品单独标注。浏览不依赖当前任务预算或用途。

“咨询这台”把商品带回聊天并预填问题，客户点击发送后才查询。咨询附件按当前目录校验精确商品 ID，本轮只读，不选定、替换或确认方案；移除附件或发送成功后清理入口参数。聊天中的整机、显示器目录链接可直接打开对应分类。

## 核心规则

- 商品只能来自数据库，演示商品与真实商品分开标注；不保存库存数量或在售状态。
- 每套主机包含 CPU、显卡、内存、主板、电源、机箱、硬盘、散热八类。
- 预算低于当前约束下最低完整配置 L：只展示超预算参考，不能确认。高于目录最高完整兼容参考 H：展示最高参考，允许节省。
- L 到 H 之间（含端点）默认总价与预算差额绝对值不超过 **500 元**；用户显式误差覆盖默认值，当前支持 0～1000 元、最多两位小数。例如 9000 元误差 50 元为 8950～9050 元，明确最多 9000 元则收紧为 8950～9000 元。规则统一在 `backend/rules/budget.ts`。
- L/H 按当前目录、购买方式及用户约束计算，不是固定档位。区间内也可能因价格离散而无匹配；搜索达到计算上限时报告搜索不完整，不能据此宣称无解或全局最优。
- DIY 拒绝已知兼容冲突，缺失资料和推定规格保留待确认；交付审核通过不代表全部厂家规格、BIOS 或满载散热已验证。商家整机只核对商品、八类构成、报价、预算、配色和指定型号，不执行 DIY 兼容性审核，也不宣称已验证兼容。
- `color` 表示整套默认配色；`partColors` 表示用户明确的单件覆盖。机箱白色、散热黑色不等于整套白色。整套配色覆盖显卡、内存、主板、电源、机箱和散热；CPU、硬盘不参与配色。
- 黑色优先、白色备选仅在当前目录该类别没有黑色商品时回退，兼容冲突不等于没有黑色。
- 最贵指约束内最高总价，不代表性能最强。DIY 使用配件目录价之和；整机使用数据库整机售价。先配置主机，再讨论显示器。

## 商品维护

工具按业务分组，组内 `index.ts` 只导出入口；具体实现按操作命名。`build` 包含推荐、组装、整机选择、局部编辑、方案评估及建议应用；`knowledge` 只提供知识检索。`registry.ts` 统一注册和执行工具，不放配置算法。

公共交付审核位于 `backend/services/delivery-audit.ts`，由工具与页面接口共同调用；公共结构化错误位于 `backend/domain/errors.ts`。服务层不依赖工具层。目录与调用关系见 [架构说明](docs/architecture.md)。

首次读取目录使用初始化标记和 `INSERT IGNORE` 保留已有商家记录，初始化路径另含指定旧演示记录清理。种子源为 `data/seed/catalog.ts`，显示器独立维护于 `data/seed/monitors.ts`，修改后可运行 `pnpm data:export` 更新导出；改种子文件不会自动修改已初始化数据库。

扩充目录包含 Intel/AMD 多平台和八类配件的多品牌演示商品，以及明确标注的演示整机组合。新增价格按通用知识估算，不代表实时行情或商家报价；缺失规格使用逐字段标记的推定值，仅用于候选初筛，BIOS 仍未验证。原有商家商品与报价保留，新增记录使用 `demo: true`，资料参考状态与估价依据写在配件规格中。

商家数据使用 `{ "parts": [...], "prebuilts": [...] }` JSON，每条配件与整机记录均须明确填写布尔值 `demo`。`node scripts/prepare-import.mjs <文件路径>` 验证数据并生成本地导入 SQL，不自动执行；完整目录替换前应备份。整机导入核对八类完整引用，不执行 DIY 兼容性审核。当前对话中的方案在后续业务操作时仍须按最新目录审核。线上商品管理后台尚未提供。

## 检查与边界

```powershell
pnpm typecheck
pnpm lint
pnpm build
pnpm test
```

`pnpm test` 覆盖基础规则与工具场景，`pnpm test:tools` 单独执行隔离工具场景。`pnpm test:model` 显式读取本地模型配置，使用演示夹具验证单轮工具选择，以及在内存中传递上下文的连续六轮对话，包含跨轮组合指代和确认边界；会调用模型但不写入生产数据。场景与验证范围见 [工具场景](docs/tool-scenarios.md)。旧 `scripts/chat-regression.mjs` 仍使用旧JSON协议，不作为当前流式接口验收依据。

页面“确认这套主机”会审核并保存整套确认状态，局部修改后旧确认失效。显示器目录包含 50 个真实型号，必须在当前任务已形成完整主机方案后才能筛选推荐；显示器不计入主机报价或确认状态。订单付款、商家权限后台不在当前已完成功能内。早期验证记录仅描述当时版本，不代表新增流程已完成线上验收。

2026-09-13 当前工作区已完成：239 项自动化测试通过，类型检查、代码检查及生产构建通过。未把这组结果视为当前真实模型、数据库、浏览器交互或线上负载的完整验收。`backend/tests/model-request-routing.ts` 提供另外的真实模型动作路由检查，未加入默认测试入口。带日期的历史验证与审查记录可能涉及已经移除的恢复行为，应结合当时快照阅读。

## 部署与运行限制

```powershell
pnpm build
pnpm start
```

使用可运行 Node.js 的服务环境，提供 MySQL 连接及服务端环境变量；这不是静态页面导出项目。反向代理应透传流式响应、关闭相应缓冲并提供足够的请求时间，当前聊天整轮上限为 300 秒。
