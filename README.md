# 装机研究所 · 电脑推荐 Agent

中文对话式主机选配项目，使用 TypeScript、Next.js 和 MySQL，面向单商家私有部署。模型负责理解需求、查询候选和选择工具；程序负责商品来源、八类完整性、报价、预算、配色与兼容性审核。

## 本地运行

需要 Node.js 22.13+、pnpm 和 MySQL 8。先创建使用 `utf8mb4` 的独立数据库与最小权限账号，再复制环境配置：

```powershell
Copy-Item .env.example .env.local
pnpm install
pnpm db:migrate
pnpm dev
```

在 `.env.local` 中把 `DATABASE_URL` 改为真实的 MySQL 连接地址。首次迁移会创建商品、整机、会话、任务和撤回历史表；首次读取目录会幂等写入种子商品。若要保留本项目原有本地 D1 数据，在完成 MySQL 建表后运行 `pnpm db:import-d1`，脚本会自动定位旧数据库并在单个事务中导入；重复主键会更新，不会在失败时留下半套数据。

在同一个 `.env.local` 配置 `MODEL_BASE_URL`、`MODEL_NAME`、`MODEL_API_KEY` 以及 `EMBEDDING_API_KEY`、`EMBEDDING_BASE_URL`、`EMBEDDING_MODEL`，然后重启服务。模型地址使用 HTTPS，基础地址包含 `/v1` 等前缀；服务需支持 Chat Completions、工具调用和 SSE streaming。Embedding 基础地址填写到 `/v1` 等 API 前缀，不包含末尾 `/embeddings`，程序会自动追加；服务需支持 OpenAI 兼容 Embeddings 接口。密钥只保存在服务端，不提交 Git。当前聊天流程需要模型配置，不能将底层规则搜索视为独立的无模型聊天模式。

## 当前功能

- 多任务需求保存、切换、恢复和当前任务重置。
- 正常推荐在同一预算允许区间内探索低价、均衡、高价方案。服务端先搜索候选，再并发执行模型选型；候选不足时如实展示，不重复凑数。明确最贵、最便宜或预算极端参考使用单套方案。
- 模型流式响应在服务端组装；聊天接口以 NDJSON 推送当前查询、选型、修正与审核进度。共享候选准备完后，低价、均衡、高价方案独立并行，固定三卡原位更新，详细过程默认折叠，不逐条自动滚动。
- 每套方案经过最新目录审核后即可展开只读预览，不必等其他分支。整批最终重审并保存后才允许选择、替换或确认；失败或新一轮生成会撤回失效预览，候选不足三套时如实展示实际数量。每个独立方案分支最多进行 3 轮候选修正；知识或目录只读查询不计入修正次数，重新启动相同需求的推荐不能重置本轮额度，且不得提交重复组合。
- 配置交付、局部替换、确认和旧方案恢复均经过统一程序审核。未知规格保留待确认；缺少 BIOS、接口或尺寸资料时，知识检索只能提供证据，不能绕过兼容性审核；不编造规格、FPS、1% low 或性能统计。
- 知识检索使用 Embedding 向量召回，向量仅缓存在服务进程内；Embedding 只改变知识召回方式，数据库商品查询与统一兼容性审核流程保持不变。

## 局部修改与撤回

`select_plan` 保存用户选定的具体方案，选择与最终确认分开；页面按钮与聊天工具共用业务服务，刷新任务后仍能找到当前方案。后续解释、评估、替换查询和局部修改可以使用已选定或唯一方案，多套未选定时必须明确对象。

`find_replacements` 支持单件查询和 `items` 数组指定的多件联动查询，固定未指定的配件，对每个组合整体审核，返回总价、兼容性、拒绝原因、颜色变更预览和分页。它不修改配置；用户允许替换后再调用 `replace_parts` 一次提交整组并重新审核。组合按类别顺序和各类价格展开分页，不代表全局总价排序；一页无可用项不能推断整个目录无解。

替换查询条件和结果随聊天历史保存，供下一轮继续引用。同方案新增联动类别时，原类别省略的过滤条件沿用最近查询；明确取消型号或品牌条件时传空字符串，取消颜色限制时传“不限”。查询记录不改变配置和确认状态。

用户询问某款配件或整套方案的选择原因时，`explain_selection` 只读返回当前商品规格、用途约束、知识库依据和候选排序共用的预算分配权重。回答聚焦为什么适合当前需求，可按八类详细解释，不追溯淘汰其他候选，不修改配置。询问改进或比较时使用只读评估；只有用户明确接受具体建议才执行。多条建议下“这个”等指代不清时先澄清，不自动执行。权重表示业务预算偏好，不是模型内部参数或实测性能。

已有 DIY 方案只换一件或几件时，模型先查询新商品，再调用 `replace_parts`；页面替换入口使用同一业务服务。未指定替换的配件 ID 保持不变，整体重新报价与审核。替换失败时原方案保留，不自动换掉其他配件来凑预算。多套方案指代不清时需先确定哪一套；修改成功后保留被修改的这一套，其他旧候选不继续冒充符合新需求。

例如：

- “均衡方案的显卡换成5070，其他不动”：只替换该套显卡。
- “机箱换白色，其他保持”：只替换机箱，单独记录机箱颜色。
- “撤回刚才的更改”：调用 `undo_last_change`，恢复当前任务上一操作前的需求与方案，不重新生成。

每条聊天消息中的多次状态保存共用一份修改前快照，页面替换按一次操作记录。连续多轮撤回可逐次恢复更早操作。历史从启用该功能后开始记录，无法找回此前没有保存的快照；任务重置和清除会话不属于本功能的撤回范围。

恢复方案需按恢复后的需求与最新目录重新审核。商品删除、报价变化或约束不满足时拒绝恢复，保留当前状态并返回原因。撤回不抹去聊天记录，也不执行订单或付款撤销。

商家整机只接受目录内实际组合，不能当作 DIY 拆换；转为 DIY 需要用户明确同意。

## 核心规则

- 商品只能来自数据库，演示商品与真实商品分开标注；不保存库存数量或在售状态。
- 每套主机包含 CPU、显卡、内存、主板、电源、机箱、硬盘、散热八类。
- 预算低于当前约束下最低完整配置 L：只展示超预算参考，不能确认。高于目录最高完整兼容参考 H：展示最高参考，允许节省。
- L 到 H 之间默认总价与预算差额绝对值不超过1000元；用户明确更小误差时按其要求收紧，例如9000元误差50元为8950～9050元，硬上限再收紧上界。规则统一在 `backend/rules/budget.ts`。
- `color` 表示整套默认配色；`partColors` 表示用户明确的单件覆盖。机箱白色、散热黑色不等于整套白色。整套配色覆盖显卡、内存、主板、电源、机箱和散热；CPU、硬盘不参与配色。
- 黑色优先、白色备选仅在当前目录该类别没有黑色商品时回退，兼容冲突不等于没有黑色。
- 最贵指约束内最高总价，不代表性能最强。DIY 使用配件目录价之和；整机使用数据库整机售价。先配置主机，再讨论显示器。

## 商品维护

工具按业务分组，组内 `index.ts` 只导出入口；具体实现按操作命名。`build` 包含推荐、组装、整机选择、局部编辑、方案评估及建议应用；`knowledge` 只提供知识检索。`registry.ts` 统一注册和执行工具，不放配置算法。

公共交付审核位于 `backend/services/delivery-audit.ts`，由工具、页面接口和任务恢复共同调用；公共结构化错误位于 `backend/domain/errors.ts`。服务层不依赖工具层。目录与调用关系见 [架构说明](docs/architecture.md)。

首次读取目录会初始化商品，后续不会覆盖已维护的数据库。种子源为 `data/seed/catalog.ts`，修改后可运行 `pnpm data:export` 更新 JSON 导出；改种子文件不会自动修改已有数据库。

商家数据使用 `{ "parts": [...], "prebuilts": [...] }` JSON。`node scripts/prepare-import.mjs <文件路径>` 验证数据并生成本地导入 SQL，不自动执行；完整目录替换前应备份。线上商品管理后台尚未提供。

## 检查与边界

```powershell
pnpm typecheck
pnpm lint
pnpm build
pnpm test
```

`pnpm test` 覆盖基础规则与工具场景，`pnpm test:tools` 单独执行隔离工具场景。`pnpm test:model` 显式读取本地模型配置，使用演示夹具验证单轮工具选择，以及保留历史和任务状态的连续六轮对话，包含跨轮组合指代和确认边界；会调用模型但不修改生产任务数据库。场景与验证范围见 [工具场景](docs/tool-scenarios.md)。旧 `scripts/chat-regression.mjs` 仍使用旧JSON协议，不作为当前流式接口验收依据。

页面“确认这套主机”会审核并保存整套确认状态，局部修改后旧确认失效。显示器目录与推荐、订单付款、商家权限后台不在当前已完成功能内。早期验证记录仅描述当时版本，不代表新增流程已完成线上验收。
