> 历史快照说明：本文记录 2026-09-12 的审查与当时修复，涉及 Cookie 恢复、多任务和撤回的描述不适用于当前一次性页面会话版本。当前行为及迁移说明以 [README](../README.md) 和 [架构说明](architecture.md) 为准。

审查日期：2026-09-12。范围为本项目的 Agent 执行底座与业务主链：用户消息 → 需求保存 → 工具调用 → 候选生成 → 统一审核 → 保存 → 前端显示，以及替换、确认、撤回、售后与显示器入口。

审查基线：HEAD `3017401` 加当时的未提交改动。用户随后授权自行修复，已按下面的修复进展修改业务代码；未修改 `.env.local`。同目录还存在其他任务的并行改动，验证结果针对执行检查时的工作区，不是某个已提交版本的验收证明。

## 修复进展（2026-09-12）

正常主链已改为：用户消息 → 在同一个模型循环内声明本轮动作 → 保存用户需求 → 查询目录并生成候选 → 统一交付审核 → 保存 → 返回完整状态。结束条件读取本轮动作和工具执行事实，不再匹配助手承诺措辞；已有旧方案也不能替代本轮重新推荐的结果。

| 路径 | 已实施修复与当前行为 |
| --- | --- |
| 新配机、整体重配 | 先保存明确需求；预算用途齐全后必须本轮执行推荐，不能只回复“正在准备”。 |
| 暂不生成、咨询、澄清 | 单独记录动作；仅保存需求不会触发推荐，咨询不会顺手改需求或清空已有方案。 |
| 选定、替换、解释、评估 | 声明具体工具动作后，必须真正调用对应工具才能结束；执行失败时依据工具问题处理。选为讨论对象调用 `select_plan(confirm=false)`，与整单确认分开。 |
| 多套方案的局部确认 | 先解析已选定或唯一方案；多套未选定返回歧义，不能默认确认第一套草稿配件；引用当前真实用户消息。 |
| 预算与审核 | 推荐、组装、替换、评估和恢复共用当前购买方式下的目录 L/H；预算高于 H 必须使用最高参考，最贵要求也在审核中校验。 |
| 保存失败 | 需求及候选状态在相应保存成功后才写入运行态；最终保存失败时只保留此前已成功保存的配件状态，不展示未保存方案。聊天失败后前端重新读取服务端状态。 |
| 刷新与运行资源 | 首次载入通过 GET 恢复 Cookie 对应会话；显式新会话仍使用 PUT。生产与开发进程均复用数据库连接池。 |

Embedding 的位置保持清晰：商品选型、价格计算、兼容性和交付审核均走数据库与程序规则；选择解释、方案评估及知识问答才调用知识检索。检索失败时保留可核对的数据库规格和审核事实，并明确提示“知识检索不可用”；不回退关键词或补写未取得的厂家参数。解释提供当前选择依据，不等同于保存了生成时所有被淘汰候选的历史比较。

候选探索原有的有限修正、种子回退和超时策略保持不变；本次没有因为某个模型回复失败就增加候选次数或绕开统一审核。

工作区完整程序测试 167 项通过，包含预算边界、多方案局部确认、动作完成条件、会话恢复和保存失败注入。授权及评估也改为保存成功后才提交运行态；评估失败保留原待评估标记，允许后续重试。类型检查、代码检查和生产构建通过。测试总数包含同目录其他任务的测试，不代表这些改动均由本任务完成。

真实模型连续六轮检查已通过：选定方案 → 只查显卡 → 查询显卡与电源联动组合 → 跨轮接受第二组并替换 → 解释匹配关系但不改配置 → 整单确认。实际执行业务工具和统一审核，使用隔离演示目录及内存保存，没有写真实任务数据库；其中解释在缺少 Embedding 配置时验证了降级回复。

空任务真实模型入口另有 2/2 通过：预算 8000 元、游戏、直接配机，实际执行需求保存和推荐，交付两套八类完整且通过审核的方案；相同需求明确“先保存、暂不生成”，只保存一次，零次生成工具、零套方案。独立脚本为 `backend/tests/model-request-routing.ts`，不加入默认测试入口，避免普通测试访问真实模型。

并行任务随后补充了真实接口与生产构建浏览器的验收记录，见 [正确性与稳定性改进验证](stability-validation-2026-09-12.md)：独立会话中完成生成、选定、确认、单件替换、重新确认、导出与过期版本拒绝；浏览器替换清除旧确认，硬刷新恢复最新任务，显示器保存后仍可继续修改主机。本任务核对了该记录，没有重复执行其操作。该任务记录的 165 项程序测试与本任务的 167 项属于不同检查快照，分别保留。

中断恢复、真实 MySQL 故障注入及生产负载仍未完成验收；并行任务也未执行真实商品导入或验证 Word 分页外观。现有实测覆盖一个独立场景，不能推广为所有链路均正常。下文保留初始审查的反例、原行号与修复路线，属于**修复前快照**，不应把其中的“当前缺口”当作修复后的状态。

## 初始审查：总体判断

项目已有可用的执行底座，具备工具白名单、服务端参数校验、独立候选分支、统一交付审核、任务版本控制与撤回事务。下一阶段应先收敛状态与规则的一致性，再扩功能。

目前最需要解决的是三类问题：同一个业务事实在不同阶段发生变化；程序结束条件仍依赖模型措辞；部分恢复与运行保障只在开发或正常完成路径成立。新增更多提示词不能替代这些修复。

| 模块 | 已有能力 | 当前缺口 |
| --- | --- | --- |
| 对话调度 | 按状态开放工具，16 轮上限，只读评估限制 | 没有完整的本轮动作状态；结束判定依赖助手文本 |
| 候选探索 | 程序搜索后分支探索、去重、实时审核预览 | 修正额度与原始候选回退计数不一致，失败归因不足 |
| 业务规则 | 八类完整性、六类配色、已知兼容冲突、预算规则集中 | 混合购买模式的 L/H 口径不一致；极值要求未在审核闭合 |
| 数据与恢复 | 会话归属、任务版本、操作快照、撤回事务 | 生产连接池不复用；刷新初始化切到新会话 |
| 前端状态 | 聊天请求序号、分支 generationId、失败撤回预览 | 失败后的已保存状态与页面状态缺少统一收敛 |
| 知识与售后 | 独立 Embedding、知识来源、售后步骤 ID 校验 | 召回结果不等于问题证据充分；型号资料来源仍需补齐 |
| 显示器 | 独立目录与服务，主机形成后开放 | 规格缺少逐条来源；推荐结果主要停留在当前页面/对话 |
| 验证 | 规则、工具、模拟对话、少量真实模型检查脚本 | 缺当前真实数据库、浏览器恢复与并发失败链路验收 |

## 正常使用流程补审

本节区分正常业务路径与特殊边界，不把前述问题等同于普通配机普遍失败。

- 隔离工具链验证：生成三套 → 选定一套 → 只替换显卡 → 重算到 8050 元 → 确认，执行成功；未替换的七类配件保持不变，替换后旧选择/确认状态清除。随后提交过长显卡，拒绝并保留原需求与方案。
- 使用项目种子目录、默认购买方式检查游戏主机：6000 元返回 5498/5998/6498 元三套，9000 元返回 8498/8998/9498 元三套，推荐与统一审核均为标准预算状态；3000 元返回 3147 元不可确认参考，前后状态一致。这些不是当前数据库实时报价。
- 因此，普通生成、明确选定、有效替换、重新确认的服务逻辑成立。实际用户对话是否调用正确工具、真实保存与页面恢复仍需分别验收。

补充发现：**多方案未选定时，局部确认没有核对方案对象。** `recommend_pc` 把第一套配件写入 draft.partSelections，但没有把第一套设为用户选定；`confirm_selections` 直接确认 draft 中的类别，没有经过 `resolvePlan`。隔离状态有三套、selection 为空，调用显卡局部确认仍成功，并把第一套显卡标为 confirmed。

这证明工具缺少对象歧义检查，不证明真实模型必然会在用户指代不明时调用该工具。正常逻辑应先确定方案或具体配件，或者证明各方案该配件相同，再记录确认；不能把程序默认填入的第一套当作用户的选择。

从日常使用看，优先处理刷新恢复、该执行时执行、多方案确认对象，再处理边界预算及失败恢复。连接池修复仍是生产部署前的必要事项。

## 优先修复的问题

### P1-01：生产环境没有复用连接池

**证据：已做隔离复现。** `db/index.ts:118-128` 每次调用可能创建连接池，但只在非 production 环境把池写入共享变量。独立进程设为 production，连续两次调用 `database()`，内部池对象不相同。复现没有执行 SQL，也没有连接真实数据库。

**影响：** 一个业务请求多次调用数据库入口就可能创建多个池；`connectionLimit: 10` 只限制每个池。正常业务调用没有统一关闭这些池的路径，连接数量可能随请求增长。尚未做真实生产负载测试，不能称连接耗尽已经发生。

**修复范围：** 仅调整 `db/index.ts` 的池生命周期，开发与生产都在进程内复用。保留现有事务和查询接口。

**完成标准：** production 模式多次获取数据库共用一个池；再用隔离数据库核对实际连接与事务行为。

### P1-02：刷新恢复与首次初始化互相冲突

**证据：代码确定，未做浏览器复测。** `frontend/workspace-session.ts:5-17` 用模块变量判断首次进入，并在首次调用时发送 PUT；`app/api/chat/route.ts:260-271` 的 PUT 无条件创建新会话 ID 并更新 Cookie。完整刷新会重新初始化页面模块，所以再次走 PUT。

**影响：** 旧任务不会因此被删除，但浏览器切换到新的会话，无法按原 Cookie 自动恢复。与 README 的选定方案刷新恢复、架构文档的售后刷新恢复，以及出错后的刷新提示冲突。现有测试只检查同一模块生命周期内的初始化去重和站内返回。

**修复范围：** 初始化读取现有会话，明确“新会话”操作才创建新会话；保留站内返回时重读最新状态的能力。

**完成标准：** 硬刷新保留 taskId、需求、已选方案和售后进度；明确新会话才更换身份。若产品本来要求每次刷新新开，应先明确这一取舍，并统一恢复入口与文案。

### P1-03：结束条件仍依赖助手措辞，无法保证该执行时执行

**证据：已做模拟模型复现。** `backend/agent/conversation.ts:57-70,313-337` 用 `promisesConfiguration` 的正则决定是否继续强制工具调用。这与 AGENTS.md 关于不得仅凭助手关键词控制流程的约定冲突。

隔离状态已有预算与用途、没有方案，用户明确请求配机；模拟模型只返回“请稍候，配置正在准备中。”，程序正常结束：工具调用 0 次、方案 0 套。该结果证明程序存在出口缺口，不代表真实模型已经在生产这样回答。

另一方面，`backend/tools/registry.ts:265-279` 在更新需求等工具成功后，仅凭预算与用途齐全就设置继续探索；结构中没有“本轮只咨询／明确暂不生成”的独立动作边界。现有咨询测试主要覆盖模型直接回答的路径，不能证明模型先保存需求后仍保留暂不生成意图。

**修复范围：** 在现有单模型循环内记录本轮动作、引用的用户消息与必要结果，工具开放和结束条件消费同一结构化状态。配机请求以方案已交付、明确待补需求或具体阻碍为终态；咨询、售后和局部替换有各自终态。替换完成后删除正则承诺修补实现，不再追加表达式。

**完成标准：** “请直接配好”同轮执行；“预算 8000 游戏，先记住、暂不生成”只保存需求；已有方案的重配也不能以旧方案存在为由跳过；局部替换不触发整套重配。

### P1-04：混合模式的预算边界在推荐与审核之间改变

**证据：已做隔离业务复现。** `backend/services/recommend.ts:187-198` 推荐时把符合条件的 DIY 与整机共同计算 L/H；`assembleBuild` 在 `:522` 只用 DIY 重算边界。`delivery-audit.ts:47-55` 审核 DIY 时调用后者。

隔离目录只有一套 8000 元 DIY 和一台 6000 元整机；需求为两种购买方式均可、预算 7500 元、误差 1000 元。同一套 8000 元 DIY：

| 阶段 | L | 预算状态 | 能否确认 |
| --- | --- | --- | --- |
| 推荐结果 | 6000 | standard | 可以 |
| 统一审核后 | 8000 | below_minimum_reference | 不可以 |

**影响：** 未发生用户需求或目录变化，同一方案却改变预算分类与确认资格；推荐阶段与最终展示可能互相矛盾。

**修复范围：** 统一当前购买方式及约束下的目录边界计算，推荐、组装、整机选择、替换和恢复共用相同口径。预算规则继续留在 `backend/rules/budget.ts`，不要用放宽校验掩盖差异。

**完成标准：** mode 为 diy、prebuilt、both 时，L/H 与确认资格贯穿全链一致；目录改变则明确重新计算和失效。

### P1-05：最高参考与最高价要求没有进入最终审核

**证据：已做隔离业务复现。** `backend/rules/budget.ts:50-55` 在预算高于 H 时允许 0 到预算的价格范围；`assembleBuild` 及统一审核只检查范围，没有检查必须达到 H 或符合最高价目标。`recommendDetailed` 的正常推荐入口会选择最高参考，但模型自主组装入口可以绕过这一选择结果。

隔离需求为预算 100000 元、DIY、最贵优先，目录实际 H 为 9051 元；提交 8000 元组合仍得到 `deliveryAudit.status=passed`。这里的金额均来自演示夹具，不是实际商家报价。

**修复范围：** 在统一审核中核对当前需求的极值目标；预算大于 H 的最高参考、预算区间内的最贵选择，都不能仅以“预算内”判为满足需求。用户明确改变目标时走需求更新，不由审核自行解释为允许降档。

**完成标准：** 推荐、自主组装、确认、恢复对同一极值要求给出相同结论；总价最高与性能最高继续分开表达。

## 第二批：让失败、中断与正常完成收敛到一致状态

### P2-01：已保存业务状态与消息、页面状态存在断点

**证据：代码推断，未做真实数据库故障注入。** `app/api/chat/route.ts:116-143` 在工具执行中立即保存任务，`:181-202` 只在整个模型循环正常结束后保存用户消息与助手消息。出错只发送 error；`frontend/chat.tsx:142-157` 清理预览并显示错误，没有重新读取已提交任务状态。

因此，“需求或配置保存成功 → 最终模型调用失败”可能留下数据库已更新、用户消息未保存、页面仍显示旧方案的状态。授权来源 ID 也可能指向没有保存下来的本轮消息。部分工具还先修改 runtime 再等待保存，保存失败后的内存状态需要单独核对。

建议明确一次操作的已提交状态：记录用户输入与操作关联；成功保存的任务版本可以在失败响应中恢复；工具先构造 next，再在保存成功后更新 runtime。保留当前已授权的分段保存行为，不能直接改为“失败全部丢弃”或“失败也算成功”。

验收只需覆盖几个关键断点：保存前失败、需求保存后失败、方案保存后最终回复失败，以及旧请求遇到任务切换/重置。

### P2-02：三次修正额度没有覆盖额外回退候选

**证据：已做模拟分支复现。** `backend/agent/parallel-plans.ts:209-216` 计数模型提交，`:267-276` 在初始种子未提交过时再审核并交付种子。模拟三个不同组合失败后，仍能交付第四个、额外审核通过的种子组合。

现有测试把种子列为第一个失败组合，因此没有覆盖这一分支。这里确实存在“最多三个组合”与“模型最多三个、另有种子回退”两种口径。

应先统一承诺的额度含义：若所有候选共用三次上限，种子应预留或占用额度；若保留额外固定回退，需要明确产品授权并改文档。不要在本次审查中擅自删掉回退、改变部分方案交付或增减超时。

### P2-03：缺少可复盘的一次操作记录

工具已有 `facts`，但主要记录需求/配件/报价是否改变；主循环结果中的 facts 没有被聊天接口持久化为完整执行记录。分支模型异常统一落入“超时或中断”的提示，无法区分请求失败、流格式错误和时间耗尽。

建议复用已有 messageId、taskId、version、generationId，最少记录：工具名称、执行结果码、失败类别、候选签名、审核问题、耗时、提交后的版本及最终结束原因。不记录 API 密钥或内部思考过程，不必引入大型日志平台。

## 第三批：业务质量完善

1. **数据可信度。** `loadCatalog` 会从种子补入缺失的推定规格，兼容规则保留推定标记，这是当前明确存在的行为。需在解释、导出与后续目录维护中持续保留来源，不把补入值当厂家核实。显示器种子只有统一 checkedAt 和价格口径，缺型号规格逐条来源；本轮没有查厂商页面，不能判断其规格已经正确或错误。
2. **知识证据适用性。** `retrieveKnowledge` 返回排序后的前若干条，`retrieveEvidence` 以结果非空判断 available。它证明检索返回资料，不证明资料支持具体型号结论。补少量无关查询和型号问题的反例，依据证据内容决定可回答范围；不要随意设一个未经评估的相似度阈值。
3. **显示器需求闭环。** 独立推荐入口已经成立。若需要跨刷新保留显示器筛选与选择，再增加任务内独立状态；继续不计入主机八类报价和确认。不要顺便改主机生成循环。
4. **计算与调用成本。** 审核会通过组装重新搜索边界，多方案、多次恢复会重复计算；整套解释还可能逐件发起知识查询。先有耗时证据，再按同一目录快照与需求复用边界或查询结果，不能缓存过期报价，也不应先减少审核次数。
