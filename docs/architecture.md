# 项目架构

项目使用 TypeScript、Next.js Node 运行时和 MySQL，按单商家私有部署设计，不引入租户表或租户隔离层。模型负责理解需求、查询候选及选择操作；程序负责数据来源、报价与硬约束。聊天通过服务端工具执行业务，网页配件替换直接调用同一业务服务。

对话为一次性页面会话。页面标识只保留在内存中，通过 `x-page-session` 随请求发送；`backend/session/page-session.ts` 在服务进程内用 Map 临时记录该页面的方案状态和聊天，不写 MySQL、Cookie、localStorage 或 sessionStorage。从聊天进入商品目录时，共享布局中的聊天组件保持挂载，仅隐藏主界面；站内导航复用同一页面标识，正在进行的流式输出与配置生成继续运行，返回聊天时显示最新进度或最终答复。刷新任一页面（包括目录页）、关闭页面或开始新会话均结束本次对话，重新打开使用新标识，需求、聊天、方案、选定确认及售后进度全部从空白开始。没有多任务、历史列表、旧方案恢复或撤回入口。当前流程不读写旧会话表；执行 0002 迁移会删除这些表及记录，升级前应备份需要保留的数据。

后端排查例外：聊天调用链的消息、目录快照、模型与工具调用、状态和错误可写入服务器 `logs/chat/*.jsonl`，仅供开发排查和测试，不用于恢复会话，不提供前端入口。默认保留最近 100 轮，每轮上限 8 MiB（超限记录截断标记），已知环境密钥和认证字段脱敏；日志不进入 Git。部署需使用可写且持久的服务器目录，临时容器销毁会丢失本地日志。

## 职责边界

| 目录                       | 职责                                                           |
| -------------------------- | -------------------------------------------------------------- |
| `app`、`frontend`          | HTTP接口、页面、流式进度和配置交互                             |
| `backend/agent`            | 对话循环、工具开放范围、提示词与few-shot、并行探索、模型流解析 |
| `backend/tools`            | 工具定义、参数和授权检查、执行协调、向模型返回结果             |
| `backend/services`         | 商品和配置搜索、局部编辑、评估与统一交付审核                   |
| `backend/rules`            | 预算、配色和兼容性约束                                         |
| `backend/domain`           | 共享业务类型、结构化错误与历史字段清理                         |
| `backend/db`               | 商品目录读写                                                   |
| `backend/session`          | 当前页面会话的内存状态、隔离和版本校验                         |
| `db`、`drizzle-mysql`      | MySQL 连接、表结构与数据库迁移                                 |
| `knowledge`、`backend/rag` | 知识资料与 Embedding 向量检索                                  |
| `data/seed`、`scripts`     | 初始目录、导入导出和检查脚本                                   |

## 工具组织

`registry.ts` 统一注册、分派和记录工具执行结果；`types.ts` 定义工具接口、上下文及参数结构辅助函数。工具名称保持稳定，文件拆分不改变模型调用协议。

组内 `index.ts` 只导出入口，不承载工具实现。共享辅助函数留在本组，避免通过相邻工具的实现文件互相调用。

- `build/`：`recommend.ts` 推荐、`assemble.ts` 组装、`select-prebuilt.ts` 整机选择、`edit.ts` 局部替换、`evaluate.ts` 方案评估、`apply-suggestion.ts` 应用建议、`finish-exploration.ts` 结束探索；`selection.ts` 共享方案保存逻辑。
- `requirements/`：`update.ts` 更新需求、`authorize.ts` 选择授权、`confirm.ts` 确认选择；`schema.ts` 定义需求参数，`message.ts` 校验用户消息归属，`state.ts` 清理失效的配件选择。
- `catalog/search.ts`：查询配件与整机。
- `knowledge/retrieve.ts`：检索知识。方案评估归属配置工具，不因使用知识而放在知识工具目录。

## 关键调用关系

```text
聊天 → 对话调度 → 工具注册表 → 对应工具 → 业务服务 → 硬规则
网页替换 → HTTP接口 → 局部编辑服务 → 交付审核 → 硬规则
本次对话状态更新 → 页面会话内存 → 版本校验
```

页面选择、确认、替换、显示器推荐和 Word 导出必须携带 `taskId` 与用户看到的 `expectedVersion`，由 `backend/api/plan-actions.ts` 统一核对。这里的任务 ID 仅标识本次对话的内部配置上下文，不代表可保存或切换的任务；内存状态更新使用同步版本比较，读写均复制数据，避免异步操作提前改变共享状态。响应携带完整结果、草稿和更新后的版本。`frontend/result-state.ts` 完整替换结果，防止旧确认或旧评估复活，同时拒绝迟到响应回滚较新状态。

普通聊天表达由当前 Function Calling 模型根据结构化任务状态和工具观察生成；售后由 `backend/support/reply.ts` 根据本轮工具事实呈现已有知识步骤或受控澄清问题。程序不在模型失败时用业务话术伪装成功；空回复、必要操作未完成且收尾修正耗尽，或达到轮数上限仍无最终回复时明确失败。型号、报价、预算、兼容性和交付状态以数据库与统一审核结果为准，模型不能覆盖审核结论。

每条新用户消息先在同一模型循环内通过 `set_request_action` 声明动作并引用当前消息 ID。预算用途齐全的配机请求必须先保存明确需求并实际执行本轮推荐；已有旧方案不能代替新推荐。仅保存、澄清和普通咨询不进入生成。选定、确认、换件、解释和评估等具体动作需要有对应工具执行事实后才能结束；失败依照工具返回的问题处理。选定讨论对象使用 `select_plan(confirm=false)`，整单确认才使用 `confirm=true`。完成条件不依赖助手回复中的关键词，工具可用范围会在同一批调用之间根据最新状态重算。

统一审核位于 `backend/services/delivery-audit.ts`，从数据库商品重新核对完整性、型号、配色、预算、兼容性和报价。外层统一审核是候选交付的固定门槛；缺少 BIOS、接口或尺寸资料时，知识检索只能提供证据，不能绕过审核。失败使用 `backend/domain/errors.ts` 的结构化错误返回具体原因；工具层负责决定是否继续探索。服务层不依赖 `backend/tools`。

正常推荐先由程序搜索候选，再并发进行模型探索。每个独立方案分支在外层固定审核下进行有限的内层 ReAct 候选修正，最多 3 轮；每轮提交后都重新审核，禁止同一组合重复提交。知识或目录只读查询不计入修正次数，重新启动相同需求的推荐不能重置本轮额度。分支独立重读目录、统一审核通过后发送带generationId与方案内容的进度事件，供只读预览；整批完成后最终重审并写入本次对话内存。前端按固定分支顺序更新，忽略旧批次事件，失败时移除预览。局部编辑只替换明确提交的商品ID，不搜索或改变其他配件；失败保留原方案。

聊天 GET 初始化或读取当前页面会话，POST 继续本次对话，DELETE 清除该页面会话；旧多任务 PUT/PATCH 入口已移除。用户消息 ID 仍用于明确需求来源、替换授权和确认边界，当前对话中的跨轮查询条件与指代仍保留。

商品数据库访问由共享连接池统一管理，连接凭据从服务端环境变量读取，本地可使用 `.env.local`。活动数据库声明及导入流程不再包含会话、任务或撤回数据；历史建表迁移保留，后续 `0002_drop_persisted_chat.sql` 迁移显式删除旧会话、任务和历史表及其中记录，升级前应备份需要保留的数据。

模型SSE流在服务端组装，收到 `[DONE]` 后即释放响应流，仍要求合法的结束原因，截断或不完整回复不会交付；HTTP 失败同样释放响应流。聊天接口通过NDJSON发送当前进程和最终完整状态。未审核候选不会提前展示为合格方案。型号、预算误差和单件／整套配色规则见README。

商品查询、解释、页面和 Word 导出保留演示身份。`Plan.demo` 表示整机自身或其任一配件属于演示商品，由最新目录审核重算；不能凭方案名称或候选自报标签判断。Word 摘要同时记录默认配色及生效的单件覆盖。

## 当前边界

`build/explain.ts` 提供只读选型解释依据；`services/selection-policy.ts` 保存推荐搜索和解释工具共用的用途预算权重，避免解释与实际策略分别维护。解释聚焦当前商品的适用原因，不保存或复述内部思考过程。询问改进或比较时使用只读评估；只有用户明确接受具体建议才允许执行。多条建议下“这个”等指代不清时必须澄清，不能自动应用。

`build/select.ts` 保存已有方案的选择或确认，页面入口共用 `services/select-plan.ts`。`services/resolve-plan.ts` 统一定位明确指定、已选定或唯一方案，多套未选定返回结构化选项。`build/find-replacements.ts` 调用业务服务，在固定其他配件的条件下只读验证候选。

售前推荐与售后基础排查共用同一个对话 Agent，不增加意图分类模型。故障请求不依赖购机预算、用途；通过 `retrieve_knowledge(category=support)` 使用 Embedding 向量召回步骤，再用 `update_support` 临时记录当前用户原话和选定的一个知识块。程序只展示本轮检索过的步骤，不接受模型自行编造操作；当前症状、步骤与恢复/停止状态仅保留在本次对话的 draft.support 中，刷新清空。售后更新不覆盖购机方案；本次对话内停止自行操作后仍须保持停止边界。

`knowledge/support/*.md` 是 Sol 编写的九类通用故障资料，没有经过具体厂家验证；`knowledge/support.ts` 按标题分块，售前与售后检索分开，默认售前，售后可按 topicId 查后续步骤。硬件、兼容性与售后故障知识统一使用 Embedding 检索，向量只在进程内缓存，并按 `EMBEDDING_BASE_URL`、`EMBEDDING_MODEL` 和语料内容失效；不使用向量数据库或管理路由。服务端独立配置 `EMBEDDING_API_KEY`、`EMBEDDING_BASE_URL`、`EMBEDDING_MODEL`，不复用 `MODEL_*`。任一配置缺失，或 Embedding 请求、响应格式、向量维度、零向量异常时，RAG 检索明确失败且不回退关键词。Embedding 只在显式知识检索中使用；配置生成、并行选型、商品查询、预算计算、兼容性审核和方案保存只依赖数据库及业务代码。仅用户明确要求时记录人工请求，否定、假设和入口咨询不触发；没有真实人工接口，回复“已记录转人工请求，人工服务暂未接通”。危险现象暂停自行操作，不自动转人工。恢复状态仅依据用户明确反馈，不代表根因已确认。

聊天需要配置模型。显示器使用独立 `monitors` 表与独立推荐服务，不能混入八类 DIY 配件；只有当前任务已有完整主机方案时才开放显示器工具和界面模块，显示器不计入主机报价或确认状态。订单付款、真实人工转接、商家权限后台尚未提供。隔离工具测试和少量模型路由检查不等于完整线上验收。
