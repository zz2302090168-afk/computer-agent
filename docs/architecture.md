# 项目架构

项目使用 TypeScript、Next.js Node 运行时和 MySQL，按单商家私有部署设计，不引入租户表或租户隔离层。模型负责理解需求、查询候选及选择操作；程序负责数据来源、报价与硬约束。聊天通过服务端工具执行业务，网页配件替换直接调用同一业务服务。

## 职责边界

| 目录                       | 职责                                                           |
| -------------------------- | -------------------------------------------------------------- |
| `app`、`frontend`          | HTTP接口、页面、流式进度和配置交互                             |
| `backend/agent`            | 对话循环、工具开放范围、提示词与few-shot、并行探索、模型流解析 |
| `backend/tools`            | 工具定义、参数和授权检查、执行协调、向模型返回结果             |
| `backend/services`         | 商品和配置搜索、局部编辑、评估与统一交付审核                   |
| `backend/rules`            | 预算、配色和兼容性约束                                         |
| `backend/domain`           | 共享业务类型、结构化错误与历史字段清理                         |
| `backend/db`               | 商品、任务与撤回快照读写，恢复时调用公共审核                   |
| `db`、`drizzle-mysql`      | MySQL 连接、表结构与数据库迁移                                 |
| `knowledge`、`backend/rag` | 知识资料与 Embedding 向量检索                                  |
| `data/seed`、`scripts`     | 初始目录、导入导出和检查脚本                                   |

## 工具组织

`registry.ts` 统一注册、分派和记录工具执行结果；`types.ts` 定义工具接口、上下文及参数结构辅助函数。工具名称保持稳定，文件拆分不改变模型调用协议。

组内 `index.ts` 只导出入口，不承载工具实现。共享辅助函数留在本组，避免通过相邻工具的实现文件互相调用。

- `build/`：`recommend.ts` 推荐、`assemble.ts` 组装、`select-prebuilt.ts` 整机选择、`edit.ts` 局部替换、`evaluate.ts` 方案评估、`apply-suggestion.ts` 应用建议、`finish-exploration.ts` 结束探索；`selection.ts` 共享方案保存逻辑。
- `requirements/`：`update.ts` 更新需求、`authorize.ts` 选择授权、`confirm.ts` 确认选择；`schema.ts` 定义需求参数，`message.ts` 校验用户消息归属，`state.ts` 清理失效的配件选择。
- `tasks/`：`create.ts` 创建、`switch.ts` 切换、`reset.ts` 重置、`undo.ts` 撤回；`context.ts` 同步切换后的任务上下文。
- `catalog/search.ts`：查询配件与整机。
- `knowledge/retrieve.ts`：检索知识。方案评估归属配置工具，不因使用知识而放在知识工具目录。

## 关键调用关系

```text
聊天 → 对话调度 → 工具注册表 → 对应工具 → 业务服务 → 硬规则
网页替换 → HTTP接口 → 局部编辑服务 → 交付审核 → 硬规则
任务恢复／撤回 → 任务读写 → 交付审核 → 硬规则
```

网页替换请求必须携带发起时的 taskId，接口先与会话当前任务核对，不匹配或缺失时拒绝，随后才编辑并按版本保存。

聊天最终表达统一由当前 Function Calling 模型根据结构化任务状态和工具观察生成。程序不再拼接正常回复，也不在模型失败时用业务话术伪装成功；空回复、提前结束配置探索或达到轮数上限会直接失败。型号、报价、预算、兼容性和交付状态仍以数据库与统一审核结果为准，模型只能解释这些事实，不能覆盖审核结论。

统一审核位于 `backend/services/delivery-audit.ts`，从数据库商品重新核对完整性、型号、配色、预算、兼容性和报价。外层统一审核是候选交付的固定门槛；缺少 BIOS、接口或尺寸资料时，知识检索只能提供证据，不能绕过审核。失败使用 `backend/domain/errors.ts` 的结构化错误返回具体原因；工具层负责决定是否继续探索。服务层不依赖 `backend/tools`。

正常推荐先由程序搜索候选，再并发进行模型探索。每个独立方案分支在外层固定审核下进行有限的内层 ReAct 候选修正，最多 3 轮；每轮提交后都重新审核，禁止同一组合重复提交。知识或目录只读查询不计入修正次数，重新启动相同需求的推荐不能重置本轮额度。分支独立重读目录、统一审核通过后发送带generationId与方案内容的进度事件，供只读预览；整批完成后最终重审并保存。前端按固定分支顺序更新，忽略旧批次事件，失败时撤回预览。局部编辑只替换明确提交的商品ID，不搜索或改变其他配件；失败保留原方案。撤回按任务快照恢复需求与方案，并重新审核，不重新选型。

同一聊天消息的多次保存共用操作ID，保存一份修改前快照。数据库更新受会话、任务ID和版本限制；重置更换任务ID，防止旧请求覆盖新任务。

数据库访问由共享连接池统一管理；批量写入和撤回使用 MySQL 事务，撤回会锁定当前任务行后再恢复快照，保持版本检查与历史删除原子化。连接凭据仅从服务端 `.env.local` 读取。

模型SSE流在服务端组装，聊天接口通过NDJSON发送当前进程和最终完整状态。未审核候选不会提前展示为合格方案。型号、预算误差和单件／整套配色规则见README。

## 当前边界

`build/explain.ts` 提供只读选型解释依据；`services/selection-policy.ts` 保存推荐搜索和解释工具共用的用途预算权重，避免解释与实际策略分别维护。解释聚焦当前商品的适用原因，不保存或复述内部思考过程。询问改进或比较时使用只读评估；只有用户明确接受具体建议才允许执行。多条建议下“这个”等指代不清时必须澄清，不能自动应用。

`build/select.ts` 保存已有方案的选择或确认，页面入口共用 `services/select-plan.ts`。`services/resolve-plan.ts` 统一定位明确指定、已选定或唯一方案，多套未选定返回结构化选项。`build/find-replacements.ts` 调用业务服务，在固定其他配件的条件下只读验证候选。

售前推荐与售后基础排查共用同一个对话 Agent，不增加意图分类模型。故障请求不依赖购机预算、用途；通过 `retrieve_knowledge(category=support)` 使用 Embedding 向量召回步骤，再用 `update_support` 保存当前用户原话和选定的一个知识块。程序只展示本轮检索过的步骤，不接受模型自行编造操作；当前症状、步骤历史和恢复/停止状态保存在任务 draft.support 中，刷新可恢复。售后更新不覆盖购机方案、不进入配置撤回栈；恢复旧配置保留当前排查记录。

`knowledge/support/*.md` 是 Sol 编写的九类通用故障资料，没有经过具体厂家验证；`knowledge/support.ts` 按标题分块，售前与售后检索分开，默认售前，售后可按 topicId 查后续步骤。硬件、兼容性与售后故障知识统一使用 Embedding 检索，向量只在进程内缓存，并按 `EMBEDDING_BASE_URL`、`EMBEDDING_MODEL` 和语料内容失效；不使用向量数据库或管理路由。服务端独立配置 `EMBEDDING_API_KEY`、`EMBEDDING_BASE_URL`、`EMBEDDING_MODEL`，不复用 `MODEL_*`。任一配置缺失，或 Embedding 请求、响应格式、向量维度、零向量异常时，RAG 检索明确失败且不回退关键词。Embedding 只在显式知识检索中使用；配置生成、并行选型、商品查询、预算计算、兼容性审核和方案保存只依赖数据库及业务代码。仅用户明确要求时记录人工请求，否定、假设和入口咨询不触发；没有真实人工接口，回复“已记录转人工请求，人工服务暂未接通”。危险现象暂停自行操作，不自动转人工。恢复状态仅依据用户明确反馈，不代表根因已确认。

聊天需要配置模型。显示器推荐、订单付款、真实人工转接、商家权限后台尚未提供。隔离工具测试和少量模型路由检查不等于完整线上验收。
