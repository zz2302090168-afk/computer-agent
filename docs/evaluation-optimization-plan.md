# 电脑 Agent 全链路测评与调优方案

日期：2026-09-15。状态：已执行 P0 和 P1 首轮试跑及针对性调优；P1 仍有质量问题，尚未进入完整开发/验证/最终测试。执行记录见 [evaluation-execution.md](./evaluation-execution.md)。优先级由用户确定：**质量与规则正确性优先，兼顾耗时和费用。**

## 一、目标与采用原则

目标是让用户的请求被正确理解、真正执行，并得到符合当前需求和数据库事实的结果。不能以“回答像那么回事”“工具返回200”或某一个RAG分数代替任务完成。

采用顺序：

1. 不违反业务硬规则，不越过用户授权，不泄露密钥或混淆会话。
2. 提高真实任务完成率、事实正确性和必要证据覆盖，减少错误操作、遗漏和无效追问。
3. 在上述质量不下降时，缩短有效结果的等待时间，再降低调用费用。

保留修复后的v2工程基线：标题＋标签＋正文、默认top-k=4；模型使用现有配置，flash Embedding使用已验证的单条并发传输。v2的小样本实验只说明局部情况，不能作为本轮全链路验收结论。

硬规则不是调参项：预算三段、八类完整性、六类配色、型号与目录存在性、DIY兼容性、整机不宣称已审核兼容、统一交付审核、确认授权、售后停止边界和一次性页面会话均保持。超时、修正次数、失败回退与结果保留策略先测，不为提高成功率擅自放宽。

## 三、数据与可信判定

### 1. 数据分层

- **程序规则层**：复用现有测试，补未覆盖的边界、状态转换和回归反例，不重复堆相同断言。按适用购买方式的L/H及边界相邻值生成案例。
- **模型任务层**：目标160个场景家族，80开发、40验证、40最终测试。家族可含1～4轮必要对话；数量指完整场景，不是API调用次数。
- **浏览器层**：约12条关键旅程，覆盖正常完成、失败、目录往返、两种页面刷新、新会话及晚到响应，桌面与手机视口抽取必要组合。
- **故障层**：以故障注入验证程序行为；真实服务只做必要的健康和集成测试。注入失败不能冒充线上故障统计。

160个模型场景按8类各20个安排：首次DIY推荐、整机与商品咨询、需求补全/变更、局部替换与确认、解释/评估/无证据问答、普通售后推进、危险/停止/数据风险、显示器/导出/跨轮状态。每类10开发、5验证、5测试，具体例子随P0目录核验落地，运行前固定。

同一原始故障、同一商品组合及其措辞改写归为一个家族，不能拆到不同集合。已有v1/v2题和已分析过的失败全部归入开发/回归资料；不再称为独立测试。

### 2. 目录与知识

- 配机集成案例来自只读的MySQL目录快照，保留真实ID、型号、价格、规格及演示标记；不伪造真实商品。
- 受控程序测试可用明确标注的隔离夹具。基于真实目录子集建立可穷举的小案例，检查搜索和审核；模拟异常资料只进入夹具，不回写目录。
- 固定目录/知识/模型配置/代码/提示词/数据划分指纹。两组使用相同目录；另设“目录变化”专项验证新价格、新规格与删除商品的处理。
- **注意现有 `loadCatalog` 在未初始化时会写入种子数据。** P0不能把调用它视为只读采样；先用只读查询检查初始化状态并导出快照。初始化、迁移、故障注入均在隔离数据库验证，不借评测改生产库。

### 3. 怎样判断对错

- 每题记录：输入与历史、初始状态、允许/禁止动作、所需事实/证据、预期终态、适用规则、可接受替代方案及严重程度。
- **能由程序判定的交给程序**：真实ID、总价、授权范围、八类、需求字段、确认/停止状态等。端到端判定不能只是再调用被测审核器并相信它；关键断言应依据独立标注和小目录穷举结果。
- **需要语义判断的建立审查包**：回答是否支持、是否遗漏、步骤是否适用。由人工核验形成可信参考；若尚无人核验，明确标为自动辅助结论，不宣称人工真值。
- 当前业务judge已知会漏判“多步操作”。先建立20个校准难例，覆盖多步、否定、引文张冠李戴、来源冒充、恰当拒答、危险继续和虚构服务；不能只校准JSON格式。
- 业务judge、Faithfulness、检索指标分别报告。固定评审规则与版本，隐藏实验组名；不重试挑选好分、不删除失败、不用平均分抵消严重错误。更换评审协议时对整批公平重评并保留旧结果。
- 若人工核验未具备，先执行有独立程序依据的评测和调优；语义质量门槛保持“待核验”，不阻塞无关工作，也不把自动评分升级为已验收。

## 四、指标与采用门槛

### 主指标

**完整任务成功率**：在未违反硬规则的前提下，完成用户本轮意图且最终页面/状态/答复一致。对咨询而言，正确回答且不改方案是成功；对无解或缺证据而言，如实说明/恰当澄清是成功。失败、超时、无效输出都保留在分母。

分别报告8类场景与宏平均，并列出原始成功数/总数。硬规则错误单列，不揉进综合分。字段正确、证据覆盖、工具调用和程序搜索指标用于解释原因，不替代主指标。

### 采用门槛（执行前固定）

1. 硬规则、授权、售后危险继续、跨会话串扰、密钥暴露等已覆盖案例：零违规。出现一例即停止推广该候选，先修复并补开发回归。零违规仅说明本次样本，没有“风险为零”的含义。
2. 质量型优化：开发/验证集完整任务成功率优于基线，严重类别无回归；最终测试不能出现新的关键失败。跨场景收益不稳定或不确定时保留基线。
3. 速度/费用型优化：主要与分场景质量均不能显示实质退步，再判断收益；目标为同等质量下完成耗时下降约20%或单成功任务调用成本下降约15%。这两个数字是筛选目标，不是预先承诺的结果。
4. 最终候选在固定测试集与基线各做3次独立运行，成对交替顺序。对随机输出按场景家族汇总，报告差异及不确定性；样本不足以排除重要退步时，不宣称非劣或稳定提升。
5. 没有胜出方案也算有效实验结果：保留基线，说明排除了什么。不能为了交付“优化成功”而调低标准。

### 耗时与费用口径

- 区分请求开始、首个状态提示、首段有用正文、首个已审核方案、最终完成。服务端耗时与浏览器可见耗时分开。
- 分解数据库、上下文组装、模型、工具、候选搜索、审核、Embedding冷索引/查询、网络与页面显示；并行耗时不能直接相加。
- 冷缓存、热缓存、成功、失败、多轮不同长度分别统计。先给中位数与范围；P95仅在同类路径取得足够样本时报告，不用混合几十个样本装作稳定尾延迟。
- 统计模型实际调用量和服务返回Token；没有用量/合同价格则金额未知。按完整用户任务及成功任务分别计算费用；失败和修正开销不能丢掉。应用费、评测费、索引费分开。

## 五、调优实验顺序

### E1：需求与工具执行

优先处理实测出现的意图混淆、限制遗漏、只承诺不执行、无效追问、重复工具。一次只改提示结构、工具说明或必要的状态呈现之一。每次保留“纯咨询/暂不生成/售后/只查替换”的相邻反例，不能靠强制生成提高推荐完成率。

### E2：候选生成、审核与数据链

先用小目录精确判定有解/无解和最高/最低可行总价，再检查生产搜索。比较程序种子与模型分支最终结果，量化模型选型新增的有效收益和成本。仅在离线隔离实验中对照“已审核程序种子”和“经过模型改进的已审核候选”；不去除统一审核，不改变线上分支/回退规则。

先优化重复过滤、等价计算和候选资料冗余。限制条件、未知资料、失败种子、分支唯一性和取消都要保留；用例没证实等价的剪枝不采用。

### E3：知识检索与上下文

按“漏的是哪类证据”选择实验，不把所有组合全排列：

1. 先修正来源、过时规则、正文缺失，单独版本化语料，重建基线。
2. 销售知识比较按结论分块与当前块；售后维持可交付步骤的原子性和稳定knowledgeId，不把多个操作合成一条以提高召回。
3. 比较原查询与添加明确结构化事实的查询；不把推测或否定内容变成肯定条件。
4. 有词面匹配漏检证据时，试词面＋向量混合；有召回足够但排名差时，再试重排。候选池先用8/10，最终上下文先保持4；若需更多再在开发集验证。
5. 检查上下文去重与排序，保留必要停止/来源边界。当前标题/标签实验作为既有参照，不无条件重跑所有组合。

新增Embedding或重排模型只有在现有服务可用且能力核实后作为独立候选，不把更换模型、分块和提示词同时混在一组。

### E4：生成模型与提示词

先在当前模型上比较更清楚的任务约束、去重复提示和结构化事实呈现；压缩上下文必须核对否定、预算、授权来源、已做步骤及停止状态是否丢失。温度、输出预算、可用模型一次只变一个因素，不能用截断答复制造省钱。

售后先核对“模型提示所要求的输出”和“程序最终交付”的一致性，分别评价步骤选择与用户最终收到的文字。不给线上增加额外LLM审核或意图分类调用。

### E5：交互与工程耗时

在已测出的慢阶段优化：连接复用、同轮不变数据复用、无依赖工作的并行、工具结果精简和页面渲染。改善首个状态提示不能冒充缩短真正交付时间。基于目录版本的缓存不能导致调价后仍交付旧价；不缓存持久对话或任务。

所有故障行为先按当前合同验证；必要的产品行为变化另形成具体变更说明，不混入普通性能调参。

## 六、消融与组合验证

每个保留改动记录“问题→假设→唯一变化→开发/验证结果”。只有各自有证据的候选才组合。对最终组合做逐项移除：去查询补充、去词面分支、去重排、恢复旧上下文、恢复旧工具说明等；只对实际新增/修改的项消融。

强交互项做小规模二因素对照，例如“混合检索×重排”“上下文压缩×模型”。所有消融仍须完整经过硬规则、授权和交付审核；禁用审核、去掉停止条件、放宽预算不属于合法消融。

先在开发/验证集完成消融，再锁定一个最终候选，使用未打开的测试集做基线对照。最终测试失败时保留基线；若据此继续修改，原测试集转为开发资料，另建新测试集。

## 七、分阶段执行与费用控制

| 阶段 | 工作与产物 | 进入下一阶段的条件 |
|---|---|---|
| P0 基线与覆盖清单 | 固定当前代码/配置/知识；只读核验目录；盘点现有测试、缺口和计时点；写场景规则及划分清单 | 硬规则解释一致，环境可执行，没有把旧会话恢复文档当需求 |
| P1 判定器与小规模试跑 | 先做8类各3个开发场景，共24个；校准程序判定和语义评审；记录完整调用链与费用用量 | 能定位失败阶段，应用失败与评审失败分开；发现基线硬错先修复并重冻，不在坏基线上调参 |
| P2 全链路基线 | 完成80开发＋40验证场景；必要浏览器旅程和隔离故障矩阵；形成按部分的好/坏清单 | 明确最影响质量的前几个问题及时间/调用成本大头；最终40题保持封存 |
| P3 有针对性调优 | 按E1～E5先修质量问题；每个问题最多同时保留2个候选，局部筛选后跑受影响链路 | 候选在验证集有效且无硬规则回归；无收益即停止该方向 |
| P4 消融与最终对照 | 组合胜出改动，做逐项移除；锁定候选后40测试题×2方案×3次，共240次完整场景运行 | 通过硬规则、质量和必要浏览器门槛；如有人工核验缺口如实保留待核验 |
| P5 交付 | 保留胜出实现，移除被替代的在线实现；输出冻结清单、短结论、失败案例和实际用量 | 类型检查、相关代码检查、构建通过；核心规则改动另跑完整测试 |

24场景试跑后用实际每场景模型调用数、轮数和Token估算后续开销：总调用量约为各类场景数×重复次数×观测平均调用数之和。不能把“160个场景”误说成“160次模型请求”。不用海量模型调用弥补断言缺失；能由程序测试的先用程序测。

并发从1个场景开始，健康后最多2个独立评测场景；遇到限流即停止扩量并记录，不能增加重试掩盖。共享服务并发计入实验环境。生产压测另在隔离环境做1/2/4阶梯，不未经核验直接对线上施压。

本方案不修改 `.env.local`，不写真实商品数据，不引入会话持久化。诊断仍遵守100轮/8MiB与脱敏边界。原始合成评测数据与统计在被Git忽略的评测目录，不能用于恢复用户会话。扩大日志保留不是默认优化项。

## 八、最终如何向用户汇报

每阶段主回复只给四项：**哪里好、哪里坏、采用什么、下一步做什么。** 最终提供一页总表：按部分列出基线/候选质量、耗时、用量和是否采用，另附最有代表性的失败案例。

详细JSON、日志和源码指纹留作复核附件，不让用户必须阅读长报告才能理解结论。未运行、模拟运行、真实接口、真实浏览器、人工核验分别标明。
